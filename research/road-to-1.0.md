# Дорога к 1.0: дизайн, архитектура, критерии выхода из беты

Черновик. Что должно быть сделано, чтобы снять пометку «beta», в каком порядке и что
остаётся на потом. Решения, которые ещё не приняты, собраны в конце.

## Критерии выхода из беты

Обязательно для 1.0:

1. **Классы:** экземпляры своих классов живут в регионах, ходят через `spawn`, каналы и
   `postMessage`, методы и `instanceof` работают в любом потоке.
2. **Новая раскладка объекта:** значения лежат в самом объекте, числа с плавающей точкой без
   коробок. Цель по доступу относительно обычного объекта в Turbofan: чтение поля ≤ ×1,1,
   запись ≤ ×1,3, доступ по индексу ≤ ×1,5 (сейчас ×1,2, ×1,7 и ×2,3).
3. **`Date` в регионах.** `Map` и `Set` — желательно, но 1.0 без них выйти может.
4. **Один способ работать с регионами:** `'use region'` помечает код, `region.run(fn)`
   выбирает регион (раздел 3). `#{}` и `enter()` остаются низкоуровневым API.
5. **Планировщик:** `spawn` с `await` по одной задаче ≤ 1 мкс, 1000 пустых задач ≤ 1 мс,
   лок без соперников ≤ 30 нс.
6. **Производительность на реальных сценариях:** цели и набор бенчмарков ниже.
7. **Платформы:** готовые сборки d8 и Node для Linux x64 и macOS arm64, Windows через WSL2.
8. **Безопасность:** фаззер покрывает типизированные массивы, `spawn`, каналы, локи и
   классы; ASan и TSan проходят все наши тесты; тесты Node проходят с флагом и без него.
9. **API заморожен:** что попало в 1.0, меняется только с новой мажорной версией.

На потом, после 1.0:

- новые поля у объекта после создания;
- сборка одного региона без остановки всех потоков;
- Chromium;
- `BigInt` и `Symbol` в регионах;
- перенос живого сокета между потоками (нужен только свежий, см. «Планировщик»).

## 1. Раскладка объекта: значения внутри, числа без коробок

Сейчас `JSRegionObject` — это заголовок `JSObject` (map, properties, elements), номер региона,
массив имён `keys`, массив значений `values` и `array_length`, плюс отдельный `FixedArray`
значений. Объект с тремя полями занимает около 48 байт против 24 у обычного, а каждое чтение
поля — это два обращения к памяти: сначала `values`, потом слот. Число, которое не Smi, лежит
в отдельном `HeapNumber` в памяти региона, и запись числа выделяет новую коробку.

Предлагается:

- **Запись (record):** map, номер региона, слоты полей прямо в объекте. Имена уже знает общая
  map формы, поэтому `keys` из объекта уходят в map (дескрипторы формы в shared space).
- **Массив:** map, номер региона, длина и указатель на `values` с запасом, как `elements` у
  `JSArray`. Массивам нужен рост, поэтому отдельный буфер у них остаётся.
- **Тип поля в форме:** `Tagged` или `Float64`. Поле `Float64` хранит сырые 8 байт, как поле
  `f64` у общих Wasm GC структур: это главный прецедент в V8. Форма выбирается при создании
  по первому значению.
- **Обобщение типа:** если в поле `Float64` пишут не число, map объекта меняется на форму с
  полем `Tagged` на месте. Слот 8 байт, поэтому объект не двигается. Старые формы не
  объявляются устаревшими: в других изолятах на них остаётся код, а проверка map в нём уже
  есть, так что это просто полиморфизм, без межизолятной деоптимизации.
- **Smi, `true`, `false`, `null`, `undefined`** лежат в слоте `Tagged` как есть, строки — как
  сейчас, копией в памяти региона.

Что это даёт:

- объект вдвое меньше, меньше промахов кэша (в каталоге это заметная часть разрыва);
- одно обращение к памяти вместо двух на чтение;
- запись числа без выделения памяти, а значит без пометки владельцем копий, которые стали
  мусором (сейчас запись вычисленного числа — 16 нс против 2,3).

Цена: перепахать всё, что знает про `keys`/`values` объекта: `LookupIterator`, обработчики IC,
быстрые пути Maglev и Turbofan, копию в `run`, сериализатор, сборщик, `Object.keys` и
остальные встроенные функции. Это самая большая переделка в плане, и на неё опирается всё
остальное, поэтому она первая.

## 2. Классы

Сейчас экземпляр класса в регион не положить: у объекта региона нет своего прототипа, методы
`Object.prototype` и `Array.prototype` берутся у изолята, который читает.

### Как это выглядит

```js
'use region';

class Point {
  x = 0;
  y = 0;
  #id = 0;
  constructor(x, y) { this.x = x; this.y = y; }
  length() { return Math.hypot(this.x, this.y); }
  static origin() { return new Point(0, 0); }
}

const r = new Region();
const p = r.run(() => new Point(3, 4));    // создаётся прямо в регионе, без копии
await spawn((p) => p.length(), p);          // 5, метод скомпилирован в потоке задачи
p instanceof Point;                         // true в любом потоке
Object.getPrototypeOf(p) === Point.prototype;  // true, это один объект на все потоки
new Point(1, 2);                            // вне run: обычный объект того же класса
```

Вне `'use region'` то же самое делает `Region.class(class Point { ... })`.

### Устройство: класс — это запечатанный регион

- **Объявление класса создаёт запечатанный регион класса.** В нём лежат:
  - конструктор и методы — холдеры кода, как у `Region.fn` (`JSRegionFunction`);
  - прототип — объект региона с методами;
  - статические методы и константы;
  - форма экземпляра и то, что класс захватил. Захватывать можно примитивы, данные
    запечатанных регионов, `Region.fn` и другие такие же классы; захват ищет тот же анализ,
    что у `spawn`.
- **Регион класса запечатан**, потому что на один класс ссылаются экземпляры из разных
  регионов, а ссылки между живыми регионами запрещены. Запечатанный регион читают все потоки
  без займов, и собирает его общий GC, когда на класс никто не ссылается.
- **У экземпляра настоящий прототип.** Общая map формы экземпляра указывает на прототип в
  регионе класса, поэтому `Object.getPrototypeOf`, `instanceof` и поиск методов работают как у
  обычного объекта, а прототип — один и тот же объект во всех потоках. Отдельная таблица
  «класс → прототип» на изолят не нужна.
- **Методы компилируются в каждом изоляте.** Чтение метода из прототипа даёт холдер, и изолят
  один раз компилирует из него свою функцию (как `Region.fn` сейчас) и кэширует её по номеру
  функции. Прототип неизменяем, поэтому IC и Turbofan сворачивают метод в константу без
  зависимостей от цепочки прототипов.
- **Форма** — только объявленные поля, публичные и приватные. Присваивание в конструкторе
  полю, которого нет в объявлении, даёт `TypeError` с подсказкой объявить поле. `new Point()`
  в текущем регионе сразу выделяет запись нужной формы, и конструктор пишет уже в неё.
- **Приватные поля:** имена `#x` и бренд класса — символы в регионе класса, поэтому `#x` в
  изоляте A и в изоляте B — одно и то же имя.
- **Наследование:** `extends` другого такого класса и `super` работают. `extends Array`,
  `Error` и `Map` в 1.0 не будет.
- **Вне региона** конструктор создаёт обычный объект этого же класса. При копии через канал
  или `postMessage` он сохраняет класс: сериализатор пишет номер класса и поля, получатель
  строит экземпляр того же класса. Сегодня structured clone теряет прототип.

Ограничения, которые остаются:

- класс после объявления не меняется: нельзя дописать метод в прототип или поменять
  статическое поле;
- методы не захватывают изменяемое состояние модуля;
- обычный класс, объявленный без `'use region'` и без `Region.class`, в регион не попадает.
  Угадывать «этот класс чистый, можно» — магия, которая ломается от одной строки в методе.

## 3. Один способ работать с регионами

Сейчас способов попасть в регион три (`region.run(fn)` с копией, литералы `#{}`, директива
`'use region'`), а выбрать текущий регион можно двумя (`run` и `using _ = region.enter()`).
Это путает.

### Что предлагается

Две вещи, у каждой одна роль:

- **`'use region'` помечает код.** `{}`, `[]` и классы в таком коде создаются в текущем
  регионе. Если текущего региона нет, тот же код создаёт обычные объекты и не падает, поэтому
  библиотеку с `'use region'` можно звать откуда угодно.
- **`region.run(fn)` выбирает регион.** Пока работает `fn`, регион текущий, и помеченный код
  пишет прямо в него, без копии. Если в результате есть обычные объекты, они копируются в
  регион, как сейчас: это путь для кода без пометки.

```js
'use region';
function makeRows(n) {
  const rows = [];
  for (let i = 0; i < n; i++) rows.push({ id: i, tags: ['a'] });
  return rows;
}

const r = new Region();
const rows = r.run(() => makeRows(100_000));   // всё в регионе, копии нет
const local = makeRows(10);                    // обычные объекты
```

Что уходит:

- `#{}` и `#[]` в документации больше не главный путь, но остаются как низкоуровневое API: они
  явно говорят «в регион» и падают без текущего региона;
- `enter()` остаётся низкоуровневым API, а `using` для займов и гардов работает как раньше.
  Его цену чиним в форке отдельно: блок с одним ресурсом без `await using` переводится в
  `try`/`finally` без `DisposableStack`, это же кандидат на CL в апстрим.

### Цена

- Литералы помеченного кода проверяют, есть ли текущий регион: одна загрузка и сравнение в
  машинном коде. Остальной JS ничего не платит, проверка есть только в коде с `'use region'`.
- Оптимизированный код, который видел только один из вариантов (в регионе или без), получает
  проверку с деоптимизацией на другом. Код, который зовут и так и так, держит обе ветки.

### Почему не неявный регион

Вариант «вызов помеченной функции без текущего региона открывает новый регион» рассматривал и
отбросил: `new Point()` вне `run` давал бы регион на каждую точку, а таблица регионов
рассчитана на 2^20.

## 4. Планировщик

### Что мешает сейчас

- `spawn` с `await` по одной задаче — около 6 мкс: два пробуждения потока ОС.
- 1000 пустых задач — 3,8 мс против 0,5 у Go.
- Лок без соперников — 165 нс против 30 у Go. Это два вызова API, глобальный мьютекс каналов и
  смена владельца региона.

Go и tokio чаще всего передают работу внутри своего планировщика, не будя поток.

### Ограничение, которое не обойти

Задача после старта живёт в своём изоляте: её промисы и замыкания — объекты локальной кучи.
Поэтому задачи нельзя переносить между потоками посреди работы, как делает tokio.
Перераспределять можно только задачи, которые ещё не начались. Схема та же M:N, что у tokio
(N изолятов на N ядер, задачи поверх), только задача прикреплена к изоляту с первого шага.

### Что предлагается

1. **Помощь вместо ожидания.** Если поток ждёт (`await`, `join()`) задачу, которую ещё никто не
   взял, он выполняет её сам. Функция у него уже есть, данные переезжают по тем же правилам.
   Это убирает оба пробуждения у последовательного `await spawn(...)`. Аналоги: `runnext` в Go,
   LIFO-слот в tokio, помощь в ForkJoin у Java.
2. **Локальные очереди и кража.** У каждого воркера своя очередь, а общую очередь он берёт,
   когда своя пуста, и крадёт у соседей задачи, которые ещё не начались. Сейчас очередь одна на
   всех.
3. **Своё пробуждение:**
   - у воркера слово парковки и почтовый ящик без блокировок;
   - разбудить — это записать в ящик и сделать `futex_wake`, только если воркер действительно
     спит;
   - в Node спящий воркер сидит в `epoll_wait` у libuv, туда идёт `uv_async_send`, тоже только
     если он спит.
4. **Заблокированные воркеры.** `recvSync`, `writeSync` и `join()` внутри задачи держат поток.
   Планировщик помечает такой воркер и, если очередь не пуста, поднимает запасной изолят
   (с ограничением сверху), как Go при системном вызове. Иначе пул голодает.
5. **Бюджет между задачами и вводом-выводом.** Воркер в Node — это и задачи, и свой цикл libuv.
   После N задач подряд он отдаёт ход вводу-выводу, как кооперативный бюджет в tokio, чтобы
   сокеты не ждали.
6. **Лок без глобального мьютекса:** у `RwLock` своё атомарное слово, захват без соперников —
   один CAS по слову лока и один CAS по записи региона в таблице владельцев, без вызовов
   рантайма в оптимизированном коде.
7. **Свежий сокет — задаче.** Для macOS и Windows, где `SO_REUSEPORT` не балансирует: принимает
   соединение один поток, воркеру уходит дескриптор (`dup` и `uv_tcp_open` на его цикле).
   Живое соединение с прочитанными данными и TLS не переносим.

Общий для всех изолятов код (компилировать функцию задачи и методы классов один раз, а не в
каждом потоке) тоже сюда: он бьёт по холодному старту и прогреву. В V8 этого нет, это отдельная
крупная задача, и в 1.0 она не обязательна.

## 5. Производительность: цель и бенчмарки

### Цель

«В 2 раза быстрее Express + cluster» — плохая цель: сам Express в несколько раз медленнее
Fastify, и такой результат получается сменой фреймворка, без регионов. Честнее мерить против
**лучшего из Bun (несколько процессов на `reusePort`) и Fastify + cluster**, на одной машине,
с одинаковой работой в обработчике.

Где ×2 реально и где нет:

- **Простые маршруты (plaintext, маленький JSON):** регионы тут не помогают, потолок — HTTP-слой.
  У `node:http` он на JS поверх llhttp, у Bun нативный (форк uWebSockets/uSockets). Свой слой не
  пишем, а берём uWebSockets.js: это нативный аддон к Node из той же линии. Готовые бинари по ABI
  на наш Node не встанут, его надо собрать из исходников против форка. У него есть раздача
  принятых соединений по `worker_threads` (`addChildAppDescriptor`), то есть и macOS с Windows,
  где нет балансировки `SO_REUSEPORT`. Цель 1.0: с uWS.js не хуже Bun, на `node:http` не хуже
  Fastify + cluster.
- **Общее состояние в памяти** (кэш, каталог, сессии, игровое состояние): процессам нужно N
  копий или Redis, у нас одна копия на все потоки. Цель — ×2 по пропускной способности или по
  памяти при той же пропускной.
- **Тяжёлая работа внутри запроса** (сортировка, разбор, преобразование JSON, рендер): `spawn`
  раскидывает её по ядрам, а лёгкие запросы не ждут тяжёлых. Цель — ×2 по p99 при
  фиксированной нагрузке; сейчас на `/compute` p99 10 мс против 160 у Fastify.
- **Рассылка между соединениями** (WebSocket-чат, pub/sub): процессам нужен Redis pub/sub, у
  нас канал. Цель — ×2.

### Набор бенчмарков

Каждый сценарий написан идиоматично для каждого участника, код открыт, база одна и та же
(локальный Postgres). Мерим максимум запросов в секунду, p99 при фиксированной нагрузке (wrk2)
и память. Участники:

- цель: Bun с `reusePort` и Fastify + cluster;
- для сравнения: Express + cluster;
- ориентир: Go и Rust axum;
- мы на `node:http` и мы на uWebSockets.js.

1. **Типовые маршруты в стиле TechEmpower:** plaintext, JSON, один запрос в базу, 20 запросов,
   fortunes (HTML-шаблон), обновления.
2. **API с кэшем в памяти:** LRU на 1 млн ключей, 90 % попаданий, промах идёт в Postgres.
3. **Поиск по каталогу:** 1 млн товаров, фильтры, сортировка, страницы (развитие `/catalog`).
4. **SSR:** `renderToString` страницы на React.
5. **WebSocket-чат:** 10 000 клиентов, комнаты, рассылка.
6. **Смешанная нагрузка:** 95 % лёгких запросов и 5 % тяжёлых (преобразование JSON на 1 МБ);
   смотрим p99 лёгких.
7. **Загрузка файла:** CSV на 50 МБ разобрать и агрегировать.

90 тысяч против 38 на Node 26 и на `/report` 2,75 против 1,73.

Смешанная нагрузка: `/search` на 20 000 запросов в секунду и одновременно `/report` на 600
(wrk2), задержка `/search`, мс:

| | Fastify | Bun | Go | Rust | uWS, 8 процессов | регионы, uWS | регионы, uWS, без memory reducer |
|---|---|---|---|---|---|---|---|
| p99 | 28,2 | 22,1 | 85,8 | **2,7** | 3,9 | 11,7 | 8,9 |
| p99.9 | 34,9 | 31,9 | 134 | **3,2** | 5,5 | 55,9 | 12,6 |

Что из этого следует:

- **Против планки (лучший из Bun и Fastify + cluster):**
  - plaintext и JSON — ×1,15–1,2;
  - поиск по каталогу — ×1,9;
  - отчёт — ×0,92;
  - память — в 1,3–1,8 раза меньше, чем у Bun, и в 2,3–3,3 раза меньше, чем у Fastify;
  - p99 смешанной нагрузки — в 1,9–2,5 раза лучше;
  - маршруты с базой — в 2,5–8 раз хуже.
- **Маршруты с базой упираются в драйвер, а не в архитектуру.** Отдельный замер, один процесс
  на одном ядре: postgres.js — 38 мкс CPU на запрос, `pg` — 29, `Bun.sql` — 4 (он нативный).
  Регионы тут ничего не решают. Догнать Bun можно только нативным драйвером Postgres для Node,
  как uWS.js для HTTP. Это ещё одна внешняя часть, которую надо взять или написать.
- **Часть выигрыша — это движок, а не регионы.** Наш Node (V8 15.9 и сжатие указателей) на
  поиске и отчёте в 1,6–2,4 раза быстрее Node 26. Сами регионы на том же движке пока
  проигрывают процессам:
  - на поиске — 17 %, на отчёте — 43 %;
  - отчёт читает 5 000 объектов региона и сортирует их компаратором, это цена каждого доступа
    (раздел 1);
  - выигрывают регионы по памяти (1,0–1,4 ГБ против 2,4) и тем, что всё в одном процессе.
- **Хвост задержки у регионов — паузы общего GC:**
  - в Node главный изолят — это изолят общей кучи;
  - главный поток простаивает, поэтому на нём срабатывает memory reducer;
  - каждая его полная сборка общая и останавливает все 8 серверных потоков: 21–48 мс;
  - с `--no-memory-reducer` p99.9 падает с 56 до 12,6 мс.

  Сделано: memory reducer на изоляте общей кучи не запускает сборку, пока есть клиенты. p99.9 —
  12,2–12,9 мс вместо 55,9, но сервер держит 0,81–0,84 ГБ вместо 0,58: мусор главного потока
  после загрузки ждёт сборки по лимиту. Правильное решение — отдельный изолят общей кучи на
  своём потоке. Тогда полные сборки главного потока станут локальными, как у воркеров, а общей
  останется только сборка общей кучи.

### Что надо починить, чтобы туда дойти

Из сегодняшних замеров:

- отдельный изолят общей кучи в Node, чтобы полные сборки главного потока не останавливали остальные (выше);
- нативный драйвер Postgres для маршрутов с базой;
- однажды `regions.js http` упал с segfault на SIGTERM; повторить не удалось (0 из 27 прогонов), ядра нет: apport не пишет его для бинарей не из пакетов;
- проверки и раскладка объекта (раздел 1);
- задачи и пробуждения (раздел 4);
- `Region.share` копирует каталог за 22 мс: нужна сборка данных сразу в регионе без копии, то
  есть литералы, классы и `'use region'` вместо `run` с копией;
- `x % n` уходит в `fprem` (около 7,5 нс), сортировка с компаратором — около 17 нс на
  сравнение. Это V8 вообще, кандидаты на CL в апстрим.

## 6. Остальное, что закрывается к 1.0

- **`Map` и `Set`** (желательно, не обязательно): таблица (`OrderedHashMap`) в памяти региона, ключи и значения — то, что
  можно хранить в регионе. Новые типы `JSRegionMap` и `JSRegionSet`, а встроенные функции
  `Map.prototype` получают ветку для них. Ключи-объекты сравниваются по указателю, это и так
  верно, потому что объект региона один во всех потоках.
- **`Date`:** число внутри, хранить просто.
- **Платформы:** macOS arm64 для Node (Maglev для arm64 уже есть), готовые сборки Node в релизе.
- **Безопасность:** фаззер на `spawn`, каналы, локи, типизированные массивы и классы;
  долгие прогоны на сервере; ASan и TSan в CI хотя бы по ночам.
- **Инструменты:** `'use region'` и классы — обычный синтаксис, его понимают все. Плагин
  TypeScript нужен только для `#{}`; типы `Region.run` и классов в регионе — в `playground/`.

## Принятые решения

- Один способ: `'use region'` помечает код, `region.run(fn)` выбирает регион; `#{}` и
  `enter()` — низкоуровневое API. Своего синтаксиса блоков не делаем.
- Цену `using` чиним в форке отдельно.
- Класс — запечатанный регион с настоящим прототипом.
- Планка производительности — лучший из Bun и Fastify + cluster; Express — для сравнения.
- HTTP: uWebSockets.js, собранный против форка, вместо своего нативного слоя.
- `Map` и `Set` — желательно для 1.0, не обязательно.

## Открытые вопросы

1. **Форма класса.** Только объявленные поля (строго, предсказуемо) или форма по

2. **Функции в `'use region'`.** Становится ли функция верхнего уровня без замыкания в таком

   (тогда он едет с продолжением, как `AsyncContext`) или `run` только синхронный?
