## Создать регион {/* #region */}

`new Region()` создаёт пустой регион, владелец — текущий поток. Положить в него данные можно через `region.run(fn)`: функция выполняется как обычно, а то, что она вернула, копируется в регион вместе со всем, на что ссылается. `run` возвращает уже копию, которая лежит в регионе. Быстрее всего создавать объекты сразу в регионе: литералами `#{}` и `#[]` или в коде с директивой `'use region'` ([следующий раздел](#literals)).

<Example file="01-first-region.js" />

Копирование внутрь происходит один раз, при создании. Дальше объекты можно передавать сколько угодно раз без копий. `region.id` — номер региона, `region.owner` — номер потока-владельца (в терминах V8 — isolate; у главного потока номер 0). Номера освободившихся регионов движок раздаёт заново, так что `id` уникален только среди живых регионов.

:::caution[Важно]
Объекты, которые вы создали внутри `fn`, и объекты в регионе — разные. Если внутри функции вы сохранили ссылку на свой объект где-то снаружи, она будет указывать на обычный объект, а не на копию в регионе. Работайте с тем, что вернул `run`.
:::

## Литералы `#{}` и `#[]` {/* #literals */}

`run` копирует в регион то, что создал обычный код. Литералы `#{...}` и `#[...]` создают объект или массив сразу в текущем регионе, без промежуточного объекта в куче потока и без копии. Они включены вместе с `--harmony-regions`.

<Example file="37-literals.js" />

Литерал создаёт объект в текущем регионе, поэтому работает внутри `using _ = region.enter()` или `run()`. В задаче `spawn` текущего региона нет, туда входят явно: `using _ = Region.of(x).enter()`.

- **Ключи** — имена, строки в кавычках и короткая запись `#{ id }`.
- **Значения** — примитивы, объекты того же региона (в том числе другие `#{}` и `#[]`) и типизированные массивы, которые копируются. Литерал ничего не копирует за вас, поэтому обычный `{}` или `[]` внутри него — ошибка: вложенные объекты тоже пишутся как `#{}`, массивы — как `#[]`. Объект другого региона внутри даёт `OwnershipError`, как при записи в поле.
- **Нельзя:** spread, дырки в массиве, методы и вычисляемые ключи. Это синтаксическая ошибка.
- Форма объекта фиксирована, как у любого объекта региона. Массив растёт через `push`.

Литерал выделяет объект прямо в машинном коде, без копии и без рантайма, и стоит около 15–20 нс ([как](/region-js/ru/inside/#literals)). Это самый быстрый способ наполнить регион: 200 000 товаров литералами и `push` создаются за 74 мс, одним `run` — за 165 мс, через `run` на каждый товар — за 377 мс. `push` в массив региона тоже идёт без рантайма, около 25 нс на элемент. Замер — на странице [«Цифры»](/region-js/ru/numbers/#create).

В VS Code типы в файлах с литералами работают через расширение из `playground/`, Biome и ESLint синтаксис `#{}` пока не понимают ([подробнее](/region-js/ru/tooling/#literals)).

### Директива `'use region'` {/* #use-region */}

Если почти все объекты функции должны лежать в регионе, решётку перед каждым `{` и `[` можно не писать. Директива `'use region'` в начале функции или файла, как `'use strict'`, делает каждый `{}` в этом коде литералом `#{}`, а каждый `[]` — `#[]`. Это обычный синтаксис JavaScript, поэтому TypeScript, ESLint, Biome и Prettier такой код понимают без расширений. Директива работает с флагом `--harmony-regions`, без него это просто строка.

<Example file="42-use-region.js" />

- **Охват.** Директива действует на тело функции и на все функции внутри неё, в том числе на колбэки вроде `rows.map((r) => ({ ... }))`, даже если их вызовут позже. Параметры самой функции разобраны раньше директивы и остаются обычными. Код в `eval` директиву не наследует.
- **Текущий регион** нужен так же, как для `#{}`: `using _ = region.enter()` или `run`.
- **Деструктуризация** не меняется: `const { a } = x`, `[a, b] = [b, a]`, `({ name }) => name`. Это шаблоны, а не литералы.
- **Нельзя** то же, что в `#{}`: spread, дырки, методы, геттеры и сеттеры, `__proto__`, вычисляемые и числовые ключи. Это синтаксическая ошибка с текстом «In 'use region' code \{\} and \[\] are #\{\} and #\[\], …». В шаблонах всё это по-прежнему можно.

## Писать прямо в регион {/* #direct */}

`region.run(fn)` удобен, когда данные уже есть или их проще собрать обычным кодом: всё, что вернёт `fn`, копируется в регион одним махом. Складывать данные в регион по ходу работы удобнее литералами: войти в регион через `using _ = region.enter()` и создавать в нём объекты `#{}` и массивы `#[]`, без копии.

<Example file="35-direct.js" />

`enter()` возвращает скоуп: объявленный через `using`, он заканчивается вместе с блоком, и текущим снова становится предыдущий регион. Внутри `run(fn)` регион тоже текущий. В задаче `spawn` текущего региона нет, ведь туда может приехать несколько регионов сразу, поэтому в регион входят явно, взяв его у объекта, который приехал: `using _ = Region.of(obj).enter()`. Если объект проще собрать обычным кодом, `region.run(() => ({ ... }))` скопирует в регион его одного, текущий регион для этого не нужен.

Обычный объект в поле региона по-прежнему не кладётся: регион хранит только свои объекты. Ошибка подскажет создать его в регионе через `run()` или `#{}`. Объекты, которые уже лежат в регионе, `run` заново не копирует: если вложенные значения уже в регионе, копируется только то, что создал сам `fn`.

Для больших объёмов `run` на каждый объект — самый медленный способ: каждый вызов — отдельная копия, и 200 000 объектов, добавленных по одному, создаются в 2,3 раза дольше, чем через один `run` (377 мс против 165), и в 5 раз дольше, чем литералами. Читаются они потом так же быстро, потому что объекты с одинаковыми ключами получают одну форму, как бы их ни создали ([практика 12](/region-js/ru/practices/#build)). Поэтому `run` на один объект хорош, чтобы иногда добавить в регион то, что собрал обычный код. Большой набор быстрее собрать литералами или обычными объектами и скопировать одним `run`.

## Чтение и запись {/* #rules */}

Владелец читает и пишет поля как обычно. Но есть три правила:

- в поле можно записать число, строку, `true`/`false`, `null`, `undefined` или объект *из того же региона*;
- обычный объект из своего потока записать нельзя: он живёт вне региона, и другой поток не смог бы его прочитать. Исключение — типизированный массив: он копируется в регион ([типизированные массивы](#typed));
- набор полей у объекта фиксирован: добавить новое свойство нельзя. Отсутствующее поле читается как `undefined`. Массивы при этом растут и укорачиваются ([массивы и методы](#arrays)).

<Example file="03-read-write.js" />

Циклы и общие куски графа при копировании сохраняются: если два поля указывали на один объект, в регионе они тоже указывают на одну копию.

:::tip[Почему форма фиксирована]
Регион — как квартира с уже расставленной мебелью. Переставлять вещи внутри (менять значения полей) можно, а пристраивать новую комнату (добавлять свойство) нельзя. Благодаря этому другой поток, получив регион, видит объекты точно такой формы, какой их создали, и движку не нужно согласовывать изменения структуры между потоками.
:::

## Массивы и методы {/* #arrays */}

У объектов региона нет своего прототипа. Когда вы обращаетесь к полю, которого нет в самом объекте, движок ищет его в `Array.prototype` или `Object.prototype` того потока, который сейчас читает. Поэтому работают `for...of`, spread, `map`, `filter`, `slice`, `includes` и другие методы массивов. Массивы региона растут и укорачиваются: `push`, `pop`, `splice`, запись за концом и `length = n` работают. Лишнее место под элементы массив держит про запас, как обычный массив JS, так что серия `push` не копирует его каждый раз. Форма объектов, наоборот, фиксирована: новое поле у объекта региона добавить нельзя.

<Example file="04-arrays.js" />

Перечисление ключей тоже работает как у обычных объектов: `Object.keys`, `Object.values`, `Object.entries`, `for...in`, `JSON.stringify` (массив региона превращается в JSON-массив), `Array.isArray`, `flat`, spread объекта `{ ...obj }` и деструктуризация. Spread даёт обычный объект, в который уже можно добавлять поля. Копия при этом поверхностная: вложенные объекты остаются в регионе.

Для потока, который не владеет регионом, всё это бросает `OwnershipError`, как и обычное чтение поля (пример в разделе [«Переезд в воркер»](#move)).

:::caution[Про скорость]
Методы из `Array.prototype` (`map`, `filter`, `reduce`, `includes`), `for...of`, `Array.from` и spread массива читают массив региона напрямую и стоят почти столько же, сколько на обычном массиве. Доступ по индексу в цикле `for` медленнее обычного примерно в 2 раза: владельца оптимизированный цикл проверяет один раз, но форма и индекс проверяются на каждом обращении. Цифры — на страницах [«Цифры»](/region-js/ru/numbers/#methods) и [«Как делать и как не делать»](/region-js/ru/practices/#methods).
:::

## Что нельзя положить в регион {/* #not-allowed */}

В регион попадают только простые объекты (их прототип — `Object.prototype` или `null`), обычные массивы, типизированные массивы, примитивы, функции из `Region.fn` ([ниже](#functions)) и ручки `Region.localRef` на объекты своего потока ([ещё ниже](#local-ref)). Остальные функции, `Map`, `Set`, `Date`, `BigInt`, `Symbol`, сам `ArrayBuffer`, `DataView`, экземпляры классов, наследники `Array` и объекты из другого региона вызовут ошибку. Про типизированные массивы — [отдельный раздел](#typed).

<Example file="05-not-allowed.js" />

Экземпляр класса раньше молча копировался как обычный объект и терял класс. Теперь это ошибка: у объекта в регионе нет своего прототипа, поэтому методы класса до него всё равно бы не дошли. Если нужны данные из экземпляра, переложите их в простой объект: `region.run(() => ({ x: point.x }))`.

## Функции в регионе: `Region.fn` {/* #functions */}

Обычную функцию в регион не положить: её код и замыкание живут в куче одного потока. `Region.fn(f)` делает из функции такую, которую объекты региона могут хранить в полях и массивах. Регион держит только её исходный текст и место в файле, а каждый поток, который её прочитал, компилирует текст сам, один раз, и дальше получает ту же функцию: `a.f === b.f` для любых регионов, в которых она лежит. Вызывается она как обычная функция, `this` — объект, на котором её вызвали, а стек ошибки показывает строку, где её написали.

Раз замыкание с функцией не переезжает, ей можно пользоваться только своими аргументами, `this`, встроенными глобальными объектами (`Math`, `JSON` и т. п.) и своим именем, чтобы вызвать себя. Захваченная переменная, `this` внешней функции у стрелки, `eval`, классы и методы объектов — `TypeError` сразу в `Region.fn`, с подсказкой, что передать аргументом. Проверку делает тот же разбор, что и у `spawn` ([захват](/region-js/ru/spawn/#captures)).

<Example file="48-region-fn.js" />

Каждый регион, куда попала функция, хранит свою маленькую запись о ней, около 52 байт. Сколько бы объектов одного `run` ни ссылались на функцию, запись одна; повторная запись той же функции в поле ничего не создаёт.

В файле или функции с `'use region'` `Region.fn` не нужен: функция оттуда становится такой сама, когда её в первый раз собирается хранить объект региона, и остаётся той же функцией, так что `region.run(() => ({ area })).area === area`. Правила те же, проверка — в этот момент: функция, которой нужна переменная её замыкания, в том числе другая функция файла, даёт `TypeError` с именем этой переменной. Методы объектов (`{ m() {} }`) регион не держит, пишите `m: function () {}`. Классы такого кода тоже могут пользоваться этими функциями.

## Ссылка на объект своего потока: `Region.localRef` {/* #local-ref */}

Иногда объекту региона нужно знать про то, что в регион не положить: `Map` с кешем, обработчик, объект окна. `Region.localRef(obj)` делает для такого объекта ручку `LocalRef`, которую регион хранит как обычное значение. Сам объект остаётся в потоке, где его создали. В этом потоке `ref.deref()` возвращает его, в любом другом бросает `OwnershipError` с причиной `other-thread`. Так устроен `SendWrapper` в Rust: ручку можно отправить куда угодно, а разыменовать только дома. `ref.local` говорит, можно ли разыменовать ручку здесь.

<Example file="49-local-ref.js" />

Каждый поток читает ручку из региона как свой объект `LocalRef`, и это один и тот же объект при каждом чтении: `a.ref === b.ref`, а в потоке-создателе это та самая ручка, которую вернул `Region.localRef`. Аргументы и захваченные переменные `spawn` едут в регионе, так что ручку можно передать задаче и напрямую. `postMessage` и `send` канала копируют обычные объекты, и копия ручки ни на что бы не ссылалась, поэтому голая ручка там — ошибка «a LocalRef cannot be copied to another thread»: положите её в объект региона и отправьте его.

Объект живёт, пока жива ручка в каком-нибудь потоке или объект региона, который её держит. Ручки в регионах видит только сборка общей кучи, поэтому объект, на который осталась ссылка только из брошенного региона, отпускается не сразу, а после ближайшей общей сборки. Освобождённый регион (`free()`) свои ручки больше не держит. Цикл «объект потока ссылается на регион, регион — на объект через ручку» сам не соберётся, как цикл `Rc` в Rust: разорвите его, освободив регион или переписав поле.

## Типизированные массивы {/* #typed */}

В регион можно положить `Uint8Array`, `Float64Array` и остальные типизированные массивы, включая `BigInt64Array` и `Float16Array`. Они устроены иначе, чем объекты региона: регион хранит сам блок памяти, а при чтении поля вы получаете обычный локальный типизированный массив, который смотрит на эту память (view). Поэтому работа с ним идёт на полной скорости, как с любым типизированным массивом, без проверки владельца на каждом элементе.

<Example file="20-typed-arrays.js" timing />

- **По умолчанию массив копируется** в регион, исходный остаётся у вас и с регионом не связан. Если массив был частью большого буфера (`subarray`), копируются только его байты.
- **Без копии** — через второй аргумент `run`: `region.run(fn, [buffer])`. Память массивов, чей `ArrayBuffer` есть в этом списке, переезжает в регион, а исходный буфер отсоединяется, как после transfer в `postMessage`: его длина становится 0.
- **Сразу в регионе** — `region.typedArray(Float64Array, n)`: массив из `n` нулей, чьи байты с самого начала принадлежат региону. Это view, как и при чтении поля; заполните его и положите в `#{}`, `run` или поле — копии не будет. Так же без копии возвращается в свой регион view, прочитанный из поля, и его `subarray`. Как любой view региона, он отсоединяется, когда регион переезжает или замораживается.
- **Каждое чтение поля даёт новый view**: `state.pixels === state.pixels` — `false`, но байты те же. Сохранить view в переменную перед циклом можно и нужно.
- **Записать в поле** новый типизированный массив можно, даже другой длины: он копируется, как в `run`.
- **Нельзя:** массивы поверх `SharedArrayBuffer` и буферов с изменяемым размером, сам `ArrayBuffer` и `DataView`.

### Когда view отсоединяются {/* #typed-detach */}

Пока регион у вас, view над его памятью работают как обычно. Когда регион уезжает в другой поток или замораживается, все view владельца отсоединяются: длина становится 0, элементы читаются как `undefined`. Так же ведёт себя `ArrayBuffer` после transfer. Ошибки `OwnershipError` здесь нет, потому что проверки владельца на каждом элементе нет. После возврата региона старые view так и остаются пустыми: прочитайте поле заново и получите новый.

Читатели замороженного региона получают view только для чтения. Запись в него вне strict mode молча не проходит, в strict mode и у методов вроде `fill` и `set` бросает `TypeError`.

<p id="typed-borrow">View замороженного региона получают те же потоки, что могут читать его поля: тот, кто его заморозил, и тот, кто держит билет `borrow()`. Но у view есть своё правило. Обычное поле проверяется при каждом чтении, а view читает память напрямую. Если бы view жил дольше права читать, поток видел бы регион и после разморозки, когда в него уже пишет новый владелец. Поэтому, когда поток сдаёт последний билет, его view отсоединяются. View того, кто заморозил, отсоединяются при `thaw()` или когда он передаёт право разморозки. Внутри `spawn` билет на замороженные регионы задача берёт сама, на всё время работы ([подробнее](/region-js/ru/spawn/#frozen)).</p>

<Example file="21-typed-views.js" />

Отсюда правило: не держите view дольше, чем нужно. Прочитали поле, поработали, отпустили. После `await` задачи, переезда или `freeze` читайте поле заново. Почему для больших массивов чисел это ещё и быстрее, показано в [практике 9](/region-js/ru/practices/#typed).

## Общие данные: `Region.share` {/* #share */}

Если данные общие на всё время работы (конфиг, справочник, таблица весов) и никто не будет их менять, это `Region.share`. `region.seal()` замораживает регион навсегда: разморозить, освободить и перенести его нельзя, поэтому читают его все потоки без билетов, как `Arc<T>` в Rust. `Region.share(data)` делает всё сразу: копирует данные в новый регион, запечатывает его и возвращает копию. Вторым аргументом, как у `run`, можно передать список буферов типизированных массивов, которые переедут без копии.

<Example file="41-seal.js" />

Запечатать может владелец или тот, кто регион заморозил, в том числе пока регион читают под билетами: выданные билеты сдаются как обычно, но право разморозить пропадает. Повторный `seal()` ничего не делает. View типизированных массивов запечатанного региона доступны только для чтения и не отсоединяются никогда, ведь регион больше не изменится. View владельца, как при `freeze()`, отсоединяются в момент запечатки.

Память запечатанного региона освобождает сборщик мусора, когда на его объекты не осталось ссылок ни в одном потоке. `free()` и `using` его не освобождают. Отправляют запечатанный регион без списка transfer, задачам `spawn` и в каналы он передаётся так же, как замороженный: по ссылке.

:::note[Как это устроено]
Проверка чтения в машинном коде не изменилась: регион заморожен, и у потока в таблице чтения стоит его бит. У запечатанного региона бит ставится при первом чтении в потоке, в медленном пути, и больше не снимается: разморозки, после которой его пришлось бы снять, не будет. Когда сборщик освобождает номер региона, бит снимается во всех таблицах, так что новый регион с тем же номером снова потребует билет.
:::

## Заморозка и рассылка {/* #freeze */}

Запечатанный регион уже не изменить. Если данные нужно раздать на чтение, а потом снова писать в них, регион замораживают на время. `region.freeze()` делает регион доступным только для чтения, причём всем потокам, но читают его под билетом `borrow()` ([билеты](#borrow)). Замороженный регион отправляют без списка transfer: каждый получатель видит те же объекты. Без билета чтение у получателя бросает `OwnershipError`, это видно в выводе воркера 0. `region.frozen` показывает, заморожен ли регион. `region.thaw()` возвращает владельцу право писать.

<Example file="08-freeze-broadcast.js" />

### Кто может разморозить {/* #thaw-right */}

Разморозить регион может только тот поток, который его заморозил. Остальные получат ошибку «Region is not frozen by this isolate», даже если читают регион. Есть ли это право у текущего потока, показывает `region.frozenHere`.

Право можно передать. Если положить замороженный регион в список transfer, данные никуда не едут (они и так общие), а получатель получает право разморозить. Отправитель его теряет и дальше читает регион, как все остальные, под билетом.

<Example file="22-freeze-handover.js" />

Отдать право может только тот, у кого оно есть: если другой поток положит регион в transfer list, будет ошибка «Region was frozen by another isolate». Задача `spawn`, которая заморозила регион, возвращает право вызывающему вместе с результатом ([пример на странице про spawn](/region-js/ru/spawn/#frozen)).

## Билеты читателя: `borrow` {/* #borrow */}

`region.borrow()` выдаёт билет и увеличивает счётчик `region.readers`. Пока есть хотя бы один билет, `thaw()` не сработает. `ticket.release()` сдаёт билет. Если объявить билет через `using`, он сдастся сам при выходе из блока, даже если внутри случилось исключение.

<Example file="09-borrow.js" />

Брать билет можно в любом потоке, в том числе в воркере: `Region.of(obj).borrow()`. Без билета замороженный регион читают только тот поток, который его заморозил (или получил право разморозить), и задачи `spawn`, которые захватили регион или получили его аргументом: им билет выдаётся сам, на всё время задачи ([подробнее](/region-js/ru/spawn/#frozen)). Остальные получают `OwnershipError: region N is frozen; borrow it to read it`, и на обычных полях, и на типизированных массивах. Это касается и объекта, который пришёл через `postMessage` или канал.

Зато пока билет у вас, `thaw()` не пройдёт: он бросит «Region is still borrowed by N reader(s)». Поэтому читатель никогда не увидит разморозку посреди чтения и не прочитает устаревшее значение.

Ждать, пока билеты сдадут, не надо циклом с повторами: `await region.thawWhenFree()` разморозит регион, как только последний читатель сдаст билет, и выполнится. Если читателей нет, регион размораживается сразу. Если билет держит тот же поток и сдать его некому, промис отказывает с `DeadlockError`, а в отменённой задаче — с её `AbortError`. Когда ждут несколько `thawWhenFree()` одного региона, размораживает первый, остальные отказывают, как `thaw()` уже размороженного региона.

`region.borrowWhile(fn)` берёт билет, вызывает `fn` и сдаёт билет, когда `fn` закончилась. Если `fn` вернула промис, билет сдаётся, когда промис выполнится или отклонится. `borrowWhile` возвращает то, что вернула `fn` (для асинхронной функции — промис с её результатом). Внутри задач `spawn` для асинхронной работы нужен именно он, потому что обычный билет живёт не дольше задачи ([подробнее на странице про spawn](/region-js/ru/spawn/#borrow)).

## Освободить регион: `free` {/* #free */}

Обычно память регионов, как и любых объектов JS, освобождает сборщик мусора: когда на объекты не осталось ссылок, они исчезают. Но иногда ссылки остаются там, где их не ждёшь: в кэше, в замыкании, в забытой переменной. Тогда большие данные висят в памяти, пока на них кто-то смотрит.

`region.free()` отдаёт регион сразу, не дожидаясь, пока пропадут ссылки. После этого любое обращение к его объектам бросает `OwnershipError: region N was freed`, из любого потока и из любого кода, в том числе из уже скомпилированного. Память типизированных массивов освобождается в момент вызова, а view владельца отсоединяются. Сами объекты опустошаются при ближайшей сборке общей кучи: всё, что они держали, уходит, даже если на них ещё есть ссылки. В C такая операция оставила бы висячий указатель, а здесь она безопасна: доступ к региону и так проверяется при каждом обращении, а освобождённый регион — просто ещё одно его состояние.

Освободить можно только свой регион. Замороженный регион освобождает тот, кто его заморозил, и только когда не осталось билетов, как при `thaw()`. Регион в пути или чужой освободить нельзя. Объявленный через `using`, регион освобождается в конце блока. Если к этому времени он уехал в другой поток, `using` ничего не делает: уехавшее значение не освобождают, как в Rust.

<Example file="34-free.js" />

`region.byteSize` показывает, сколько байт региону досталось при копировании: объекты, их массивы, строки и память типизированных массивов. Это приблизительная цифра: литералы `#{}` и `#[]` и рост массивов в неё входят, а строки, записанные в поля позже, нет. `Region.stats()` показывает, сколько регионов живо, сколько освобождено, но ещё не собрано, и сколько байт держат живые.

## Переезд в воркер {/* #move */}

[`spawn`](/region-js/ru/spawn/) и [каналы](/region-js/ru/channels/) перемещают регионы сами. Если нужен свой воркер, регион передают ему напрямую, через `postMessage` со списком transfer: отправьте объекты региона через `postMessage` и укажите сам регион в списке transfer. Воркер получит те же объекты, а не копию, и станет их владельцем. Главный поток доступ потеряет.

<Example file="06-move.js" />

Переезд не зависит от размера данных: движок меняет владельца региона, а объекты остаются на месте. Копия через `postMessage` обходит каждый объект. Вот одно и то же дерево из 131 071 узла, отправленное обоими способами:

<Example file="02-before-after.js" timing />

Видно два разных текста ошибки. Сразу после отправки регион ещё в пути: «was sent to another thread and has not been received yet». Когда воркер получил сообщение, владелец уже он: «belongs to another thread». Обе ошибки заканчиваются местом отправки. `Object.keys`, `JSON.stringify` и прочее перечисление ключей проверяют владельца так же, как чтение поля.

Сам объект `region` в данные сообщения класть не нужно, достаточно объектов из него. Объекты региона всегда передаются по ссылке. Если отправить их без списка transfer, воркер получит ссылку, но прочитать по ней ничего не сможет, пока регион к нему не переедет: владелец остаётся прежним.

В списке transfer можно указать и сам объект региона, он означает свой регион: `worker.postMessage(order, [order])` работает так же, как `[region]` или `[Region.of(order)]`.

`postMessage` со списком transfer — самый низкий уровень. `spawn` делает то же самое без списка transfer и мимо `postMessage`, через свою очередь, поэтому обходится дешевле.

## Вернуть регион обратно: `Region.of` {/* #of */}

В воркере нет переменной `region`, есть только полученные объекты. `Region.of(obj)` находит регион по любому его объекту. С ним воркер может вернуть данные тем же способом. Для списка transfer хватит и самого объекта ([переезд](#move)), а `Region.of` нужен, чтобы вызвать методы региона: `borrow()`, `freeze()`, `free()`. Проверить, лежит ли значение в регионе, не ловя ошибку, можно через `Region.isRegionObject(value)`. У региона в одном потоке одна ручка: `Region.of(a) === Region.of(b)`, если `a` и `b` из одного региона, и `Region.of(obj) === region` для того `region`, в котором объект создан.

<Example file="07-ping-pong.js" timing />

Тысяча кругов «туда и обратно», и в конце в руках тот же самый объект: `current === state`. Один круг — два переезда и две пересылки сообщения — занимает около 10–11 микросекунд, от запуска к запуску по-разному.

### Ошибки {/* #errors */}

Нарушения владения бросают `OwnershipError`. Это наследник `TypeError`, так что код, который ловил `TypeError`, работает как раньше. У ошибки два поля: `region` — номер региона и `reason` — причина одним словом, по которой удобно ветвиться вместо разбора текста.

В конце текста ошибка говорит, где с регионом случилось то, из-за чего она возникла: где его отправили, разморозили, заморозили, запечатали, освободили или положили в `RwLock`. Например, `(sent at main.js:12:5)`. Код задачи `spawn` сохраняет строки своего файла, поэтому и отправка из задачи показывает место в файле. Если файла у кода нет, например у воркера из строки, будет номер потока: `(sent by isolate 2)`. Запись места стоит около 60 нс на событие, флаг d8 `--no-region-history` её выключает.

<Example file="44-errors.js" />

| Текст | `reason` | Когда бывает |
| --- | --- | --- |
| `region N belongs to another thread (isolate X, this is isolate Y)` | `not-owner` | Обращение к региону, которым владеет другой поток. |
| `region N was sent to another thread and has not been received yet` | `in-transit` | Регион отправлен, но ещё не получен: лежит в канале, в очереди задач или в сообщении. |
| `region N was freed` | `freed` | Обращение к освобождённому региону. `Region was already freed` — повторный `free()`. |
| `region N is frozen; thaw it before writing` | `frozen` | Запись в замороженный регион, в том числе владельцем. `Region is already frozen` — повторный `freeze()`. |
| `region N is frozen; borrow it to read it` | `not-borrowed` | Чтение замороженного региона без билета потоком, который его не замораживал: поля, типизированные массивы, `Object.keys` и прочее. |
| `region N is sealed and cannot change` | `sealed` | Запись в запечатанный регион. |

| `Region is sealed: its objects are shared, send them without a transfer list` | `sealed` | Запечатанный регион в списке transfer. |
| `region N is in an RwLock; use it through lock.read() or lock.write()` | `locked` | Обращение к региону, который лежит в `RwLock`, мимо guard. Своими текстами `free()`, `freeze()`, список transfer и второй `RwLock` на тот же регион. |
| `region N is locked for reading; use lock.write() to change it` | `read-locked` | Запись под `lock.read()`. |
| `Region is still borrowed by N reader(s)` | `borrowed` | `thaw()` и `free()`, пока не сданы билеты, в том числе билеты задач `spawn`, которые ещё ждут в очереди. Дождаться их — `thawWhenFree()`. |
| `Region is not frozen by this isolate` | `not-frozen` | `thaw()` в потоке, у которого нет права разморозить. |
| `Region must be frozen to borrow it` | `not-frozen` | `borrow()` у незамороженного региона. |
| `a region object cannot reference objects outside its region; create them in it with region.run() or #{}` | `outside-reference` | Запись в поле обычного объекта или объекта из другого региона. |
| `this LocalRef refers to an object of another thread (isolate X, this is isolate Y); only that thread can deref() it` | `other-thread` | `deref()` ручки `Region.localRef` не в том потоке, где её сделали. Поле `region` у этой ошибки равно −1. |

Задачи и общие данные бросают свои классы, наследники `Error`: `AbortError` (задачу отменили), `TimeoutError` (наследник `AbortError`, задача не успела за `timeout(ms)`), `DeadlockError` (все потоки ждут друг друга) и `PoisonError` (`RwLock` отравлен писателем, который не закончил работу, см. [RwLock](/region-js/ru/channels/#rwlock)).

Ошибки формы данных — обычные `TypeError`, без `region` и `reason`:

| Текст | Когда бывает |
| --- | --- |
| `Cannot add property X, region objects have a fixed shape` | Новое свойство у объекта региона. |
| `… cannot be moved into a region` | В `run` попала функция, `Map`, `Date`, `DataView`, массив поверх `SharedArrayBuffer`, экземпляр класса, наследник `Array` и т. п. |
| `#{} and #[] need a current region: use region.enter() or region.run()` | Литерал вне `enter()` и `run()`. |
| `#{} and #[] hold primitives and objects of their region; write nested objects as #{} and arrays as #[]` | Обычный объект или массив внутри литерала. |
| `In 'use region' code {} and [] are #{} and #[], which allow no spread, holes, methods, accessors, __proto__, computed or numeric keys` | Синтаксическая ошибка: в коде с `'use region'` литерал, который не может быть `#{}` или `#[]`. |
| `Region.of() expects an object from a region` | `Region.of` для обычного объекта. |
