## Шпаргалка {/* #cheatsheet */}

| Ситуация | Плохо | Хорошо | Замер: плохо → хорошо |
| --- | --- | --- | ---: |
| [1. Большие данные для многих задач](#frozen) | захватить обычный массив | заморозить регион и захватить его | 1 065 мс → 0,7 мс |
| [2. Данные ходят туда-обратно](#move) | каждый раз `region.run` | один регион, переезд через `Region.of` | 3 585 → 8,8 мкс за круг |
| [3. Много мелкой работы](#batch) | тысячи маленьких `spawn` | десятки задач по нескольку миллисекунд | 57 мс → 52 мс |
| [4а. Горячий цикл с записью](#local) | писать в объект региона на каждом шаге | считать в локальных переменных, записать один раз | 4,6 мс → 0,66 мс |
| [4б. Много проходов по массиву региона](#local-read) | читать `arr[i]` из региона каждый раз | один раз скопировать в обычный массив, `Array.from` или циклом | 13,1 мс → 3,1 мс |
| [5. Методы массива региона](#methods) | копировать массив ради `filter` / `map` | вызывать методы прямо на массиве региона | копия не нужна: 20,1 мс и 21,1 мс |
| [6. Много объектов одного вида](#shapes) | ключи в разном порядке | одни и те же ключи в одном порядке | 11,1 мс → 5,9 мс |
| [7. Ждать задачу в главном потоке](#await) | `task.join()` | `await task` | пауза 192,5 мс → 0,3 мс |
| [8. Объект после переезда](#after-move) | читать сразу после отправки | дождаться, пока регион вернётся | OwnershipError → работает |
| [9. Много чисел](#typed) | обычный массив чисел в регионе | типизированный массив в регионе | 2,4 мс → 0,68 мс |
| [10. Задачи в `map`](#map) | колбэк запускает задачу и возвращает другое | колбэк возвращает ручку задачи | задачи не дождались → дождались |
| [11. Билет в асинхронной задаче](#borrow-while) | `borrow()` и отложенное чтение | `return region.borrowWhile(async ...)` | OwnershipError → работает |
| [12. Большой набор данных в регион](#build) | `run` на каждый объект | литералы `#{}` или один `run` | 377 мс → 74 мс |

Несколько замеров разошлись с тем, что мы ожидали, и советы под них поправлены. «По одной задаче на ядро» оказалось не лучшим делением работы: десятки задач поменьше выровняли нагрузку и вышли быстрее ([3](#batch)). А создавать много объектов в регион литералом `#{}` быстрее всего, `run` на каждый объект — медленнее всего ([12](#build)).

После того как компиляторы научились встраивать доступ к регионам, выигрыш в практиках [4](#local) и [9](#typed) уменьшился: «плохие» варианты, которые ходят в регион на каждом шаге, стали примерно втрое быстрее. Советы остались, но разница теперь в разы, а не на порядок. Форма объектов ([6](#shapes)) теперь важна так же, как у обычных объектов.

Потом методы массивов, `for...of`, `Array.from` и spread научились читать массив региона напрямую, а не через рантайм на каждый элемент. Методы на массиве региона стали примерно в 10 раз быстрее и стоят почти как на обычном массиве. Поэтому практика [5](#methods) переписана: раньше она советовала заменять `filter`, `map` и `reduce` циклом (разница была в 67 раз), теперь говорит, что копия ради методов не нужна. В практике [4б](#local-read) копия через `Array.from` раньше была самым медленным вариантом, теперь она стоит столько же, сколько копия циклом.

## <span class="practice-num">1</span> Большие данные только для чтения — в замороженный регион {/* #frozen */}

Когда задача `spawn` захватывает обычный массив или объект, он копируется. Каждая задача получает свою копию, и копирует её главный поток в момент вызова. Тридцать две задачи над одним каталогом — это тридцать две копии каталога.

Замороженный регион не копируется вообще. Все задачи и главный поток читают одни и те же объекты. Платите вы один раз, когда кладёте данные в регион.

<div class="versus">

```js bad
const catalog = await loadCatalog();      // обычный массив, 100 000 товаров
const sums = await Promise.all(parts.map((k) =>
  spawn(() => sumPart(catalog, k))));     // catalog копируется в каждую задачу
```

```js good
const data = await loadCatalog();
const region = new Region();
const catalog = region.run(() => data);   // одна копия, в регион
region.freeze();                          // читать могут все задачи сразу
const sums = await Promise.all(parts.map((k) =>
  spawn(() => sumPart(catalog, k))));     // копий нет
```

</div>

<Chart id="p-frozen" />

<Example file="practice-01-frozen-shared.js" timing collapsed />

Разница примерно в 1 500 раз, и почти вся она — копирование: около 33 мс на копию каталога, тридцать две копии подряд. Сама работа в задачах тут крошечная. Если данные нужно и читать, и менять, замораживать нельзя. Тогда смотрите следующую практику.

## <span class="practice-num">2</span> Создать регион один раз и гонять его, а не пересоздавать {/* #move */}

`region.run` копирует в регион весь граф, который вернула функция: это O(n). Переезд готового региона стоит O(1), сколько бы объектов в нём ни было. Если данные ходят между потоками много раз, создайте регион один раз и дальше только передавайте его. В воркере регион находится через `Region.of(obj)`. С `spawn` то же самое: захваченный регион сам уезжает в задачу и возвращается.

<div class="versus">

```js bad
for (const step of steps) {
  const region = new Region();
  const items = region.run(() => localItems);   // 10 000 объектов копируются заново
  worker.postMessage({ items, step }, [region]);
  await nextMessage(worker);
}
```

```js good
const region = new Region();
let items = region.run(() => localItems);       // копия один раз
for (const step of steps) {
  worker.postMessage({ items, step }, [Region.of(items)]);
  items = (await nextMessage(worker)).items;    // тот же объект вернулся
}
```

</div>

<Chart id="p-move" />

<Example file="practice-02-move-not-rebuild.js" timing collapsed />

8,8 микросекунды за круг — это два сообщения и два переезда региона, от размера данных время не зависит. 3,5 мс — почти всё копия 10 000 объектов в новый регион. Чем больше данных, тем больше разница.

## <span class="practice-num">3</span> Несколько крупных задач вместо тысяч мелких {/* #batch */}

Задачи `spawn` идут в пул долгоживущих воркеров, по умолчанию их четыре (`spawn.poolSize`). Запуск одной задачи стоит около 3 микросекунд, а когда задачи запускаются тысячами сразу, около 4: упаковать аргументы, передать в воркер, получить и разобрать ответ. Если работа в задаче сопоставима с этим временем, накладные расходы её съедают. Пусть каждая задача работает хотя бы полмиллисекунды: тогда запуск займёт меньше процента её времени.

Мы ожидали, что лучше всего будет по одной задаче на воркер. Замер показал другое: если части неравны по работе, несколько задач на воркер выходят быстрее. Освободившийся воркер берёт следующую задачу из очереди и не ждёт самую долгую.

<div class="versus">

```js bad
// 10 000 задач по 200 чисел, около 20 мкс работы в каждой
const counts = await Promise.all(ranges.map(([from, to]) =>
  spawn(countPrimes, from, to)));
```

```js good
// 100 задач по 20 000 чисел, около 2 мс работы в каждой
const parts = 100;
const counts = await Promise.all(Array.from({ length: parts }, (_, i) =>
  spawn(countPrimes, Math.floor((LIMIT * i) / parts), Math.floor((LIMIT * (i + 1)) / parts))));
```

</div>

<Chart id="p-batch" />

<Example file="practice-03-batch.js" timing collapsed />

100 задач — в 3,7 раза быстрее главного потока, почти идеал для четырёх воркеров. 10 000 мелких задач заняли 57 мс: на 5 мс дольше, чем 100 задач, то есть около 0,5 мкс лишних на каждую из 10 000. Раньше, когда запуск стоил около 40 мкс, этот вариант шёл 377 мс и был вдвое медленнее той же работы в главном потоке без всякого `spawn`. Теперь разница с крупными задачами почти пропала, но совсем мелкие задачи всё равно немного проигрывают.

Четыре крупные задачи дали только ×3: проверить большое число на простоту дольше, чем маленькое, поэтому последняя четверть считается дольше первой, и три воркера в конце простаивают. В отдельной проверке мы перебрали и другие числа частей: 8 частей — около 59 мс, 16 — около 55, от 32 до 1 000 — 52–53 мс, 10 000 — около 57.

## <span class="practice-num">4</span> Горячие циклы: считать локально, в регион писать один раз {/* #local */}

Maglev и Turbofan встраивают доступ к объектам региона в машинный код ([как](/region-js/ru/inside/#jit)), а Turbofan в цикле без вызовов проверяет владельца один раз. Но проверки формы, индекса и, при записи, значения остаются на каждом обращении, а сами значения лежат в памяти. Обычная локальная переменная компилятору понятна: он держит её в регистре процессора, и проверять там нечего.

### а) Запись {/* #local-write */}

<div class="versus">

```js bad
for (let i = 0; i < values.length; i++) {
  stats.count += 1;          // stats лежит в регионе
  stats.sum += values[i];
}
```

```js good
let count = stats.count, sum = stats.sum;
for (let i = 0; i < values.length; i++) {
  count += 1;
  sum += values[i];
}
stats.count = count;         // в регион один раз
stats.sum = sum;
```

</div>

<Chart id="p-write" />

Локальные переменные быстрее в 4,2 раза. До встраивания доступа в компиляторы запись на каждом шаге занимала 14,3 мс, и разница была в 19 раз, до проверки владельца один раз на цикл — 4,6 мс и в 7 раз. Это больше, чем отставание записи на странице [«Цифры»](/region-js/ru/numbers/#access) (×1,7): там обычные объекты тоже пишут в память, а здесь локальный вариант память не трогает, обе переменные живут в регистрах. Обычный объект в этом же цикле, по отдельной проверке, занимает около 1,7 мс. Так что совет полезен и в обычном JS, а с регионами он даёт больше: на каждом шаге ещё и проверки. Чем горячее цикл, тем больше выигрыш.

### б) Много проходов по массиву региона {/* #local-read */}

Если по массиву региона нужно пройти много раз по индексу, дешевле один раз скопировать его в обычный массив. Копирует и `Array.from(arr)`, и `[...arr]`, и простой цикл: для массива региона все три делают один проход по массиву значений и стоят примерно одинаково.

<div class="versus">

```js bad
for (let pass = 0; pass < 50; pass++)
  for (let i = 0; i < prices.length; i++) total += prices[i];   // prices в регионе
```

```js good
const local = Array.from(prices);   // копия один раз, обычный массив
for (let pass = 0; pass < 50; pass++)
  for (let i = 0; i < local.length; i++) total += local[i];
```

</div>

<Chart id="p-read" />

<Example file="practice-04-local-then-write.js" timing collapsed />

Копия вместе с 50 проходами в 2,2 раза быстрее, чем 50 проходов по региону. До встраивания доступа в компиляторы проходы по региону занимали 34,6 мс, и разница была в 8,8 раза, до проверки владельца один раз на цикл — 13,1 мс и в 4 раза. Копия через `Array.from` раньше проигрывала даже проходам прямо по региону, 17,8 мс против 12,3: она шла через итератор, и каждый элемент читался через рантайм. Теперь `Array.from` и spread копируют массив региона одним проходом по значениям ([как](/region-js/ru/inside/#methods)), и выходит 3,5 мс, почти как с копией циклом (3,4 мс). Проход по обычному массиву примерно вдвое дешевле прохода по массиву региона, так что копия окупается уже через несколько проходов. Копия — это снимок. Изменения в регионе в ней не появятся, и запись в неё не попадёт в регион. Для одного прохода копировать смысла нет, об этом следующая практика. А если в массиве только числа, лучше с самого начала хранить их в типизированном массиве ([практика 9](#typed)): тогда копия не нужна вовсе.

## <span class="practice-num">5</span> Методы массива региона: вызывать прямо, без копии {/* #methods */}

У массива региона нет своего прототипа. `map`, `filter`, `reduce` и другие методы берутся из `Array.prototype` читающего потока. Раньше они читали каждый элемент через рантайм и были в десятки раз медленнее цикла, поэтому здесь советовали цикл или копию. Теперь методы, `for...of`, `Array.from` и spread читают значения прямо из массива региона ([как](/region-js/ru/inside/#methods)). Копировать массив ради методов больше не нужно.

<div class="versus">

```js bad
const local = new Array(numbers.length);   // numbers в регионе
for (let i = 0; i < numbers.length; i++) local[i] = numbers[i];
const total = local                 // копия ради методов
  .filter((x) => x % 2 === 0)
  .map((x) => x * x)
  .reduce((a, b) => a + b, 0);
```

```js good
const total = numbers               // прямо на массиве региона
  .filter((x) => x % 2 === 0)
  .map((x) => x * x)
  .reduce((a, b) => a + b, 0);
```

</div>

<Chart id="p-methods" />

<Example file="practice-05-methods.js" timing collapsed />

Методы на массиве региона занимают 23,9 мс, на обычном массиве с теми же значениями — 19,0 мс, в 1,3 раза меньше. До быстрых путей было 216 мс. Копия циклом перед методами почти ничего не даёт: 22,1 мс вместе с копией, а памяти нужно вдвое больше.

Цикл `for` по индексу по-прежнему быстрее цепочки методов, в 11 раз. Но это не особенность регионов: на обычном массиве разница такая же. Методы вызывают колбэк на каждый элемент, а `filter` и `map` ещё и создают промежуточные массивы. Так что выбирать между методами и циклом стоит так же, как в обычном JS: методы там, где важнее читаемость, цикл в самых горячих местах. Для одного прохода циклом копия тоже не нужна: 3,5 мс с копией против 2,1 мс без неё, а обычный массив проходится за 1,7 мс.

Быстрый путь работает, когда поток может читать регион: владеет им или держит билет замороженного. Иначе метод бросает `OwnershipError`, как и обычное чтение. Элементы, которые сами являются типизированными массивами, читаются по общему пути: каждый раз получается новый локальный view. Если подменить `Array.prototype[Symbol.iterator]`, `for...of`, `Array.from` и spread вызовут подменённый итератор, как и у обычного массива.

## <span class="practice-num">6</span> Одинаковая форма объектов {/* #shapes */}

У каждого объекта региона есть «форма»: набор ключей в определённом порядке. Объекты `{ x, y }` и `{ y, x }` — разные формы. Inline cache в каждом месте кода запоминает формы, которые там встречались. С одной формой он работает быстрее всего, с двумя–четырьмя (полиморфный случай) перебирает их, а дальше переходит на общий медленный путь (мегаморфный случай). Привычный совет для обычного JS — создавать однотипные объекты одинаково, одной функцией или одним литералом.

<div class="versus">

```js bad
const points = region.run(() => rows.map((r) =>
  r.fromApi ? { y: r.y, x: r.x } : { x: r.x, y: r.y }));   // две формы вперемешку
```

```js good
const makePoint = (x, y) => ({ x, y });                     // одна форма
const points = region.run(() => rows.map((r) => makePoint(r.x, r.y)));
```

</div>

<Chart id="p-shapes" />

<Example file="practice-06-shapes.js" timing collapsed />

У обычных объектов всё как в учебнике: одна форма 1,5 мс, 24 формы 7,8 мс, в 5,2 раза медленнее. У объектов региона теперь так же, только мягче: четыре формы на 24% медленнее одной, 24 формы — в 2,4 раза. Компилятор встраивает чтение поля, если во всех формах, которые видел inline cache, поле лежит в одной позиции. В этом замере у первых четырёх форм `x` идёт первым, поэтому они почти не мешают. Если позиции разные или форм слишком много (мегаморфный случай), остаётся вызов IC на каждом обращении. До встраивания доступа в компиляторы IC вызывался всегда, и 24 формы шли так же быстро, как одна (около 20 мс). Совет теперь работает так же, как для обычного JS.

Ещё видно, что сумма поля по 100 000 объектов региона с одной формой в 3 раза дольше, чем по обычным (до встраивания было в 13 раз, до проверки владельца один раз на цикл — в 4,5). Это в основном не форма, а проверки в горячем цикле: индекс по массиву региона (практика 4б) и проверка формы и владельца у каждого нового объекта: в каждой итерации это другой объект, и одна проверка на цикл его не покрывает.

## <span class="practice-num">7</span> В главном потоке — `await`, а не `join()` {/* #await */}

`task.join()` останавливает поток, пока задача не закончится. В браузере это выглядело бы как зависшая страница: клики не обрабатываются, кадры не рисуются, анимации стоят. Задача при этом считается в другом потоке, но главному от этого не легче, он просто ждёт. `await task` отпускает поток: пока задача считается, главный поток обрабатывает события, а результат приходит потом.

В d8 нет страницы, поэтому мы изобразили её цепочкой `setTimeout`: каждый «тик» — как обработка события. Пока задача считается около 0,2 с, мы считаем, сколько тиков успел сделать главный поток и какой была самая длинная пауза между ними. В d8 `setTimeout` не ждёт указанную задержку, поэтому тиков так много: цепочка крутится так быстро, как позволяет поток.

<div class="versus">

```js bad
button.onclick = () => {
  const result = spawn(buildReport, rows).join();   // страница стоит, пока считается
  render(result);
};
```

```js good
button.onclick = async () => {
  const result = await spawn(buildReport, rows);    // страница отвечает
  render(result);
};
```

</div>

<Chart id="p-await" />

<Example file="practice-07-await-not-join.js" timing collapsed />

С `join()` главный поток не ответил ни разу, пока шла задача: единственный тик случился уже после неё, и пауза равна длине задачи. С `await` он ответил около 257 тысяч раз, и самая длинная пауза — 0,3 мс. Сама задача в обоих случаях считается одинаково долго. `join()` уместен в воркере или в скрипте d8, где отвечать некому. Вызов `spawn(...).join()` подчёркивает правило Biome из [песочницы](/region-js/ru/tooling/#biome).

## <span class="practice-num">8</span> Не трогать объект, пока его регион в другом потоке {/* #after-move */}

После `postMessage(..., [region])`, после `spawn`, захватившего регион, или после отправки объекта региона в [канал](/region-js/ru/channels/#move) регион принадлежит другому потоку. Ссылка на объект у вас осталась, но любое обращение к нему бросает `OwnershipError`: и чтение поля, и `Object.keys`, и `JSON.stringify`. Это защита от гонки данных, а не ошибка движка. Дождитесь, пока регион вернётся: после `await` задачи или после ответного сообщения воркера с `Region.of(obj)` в списке transfer. Замера здесь нет: «плохой» вариант просто не работает.

<div class="versus">

```js bad
const task = spawn(() => addShipping(cart));   // cart уехал в задачу
showTotal(cart.total);                         // OwnershipError
```

```js good
const task = spawn(() => addShipping(cart));
await task;                                    // регион вернулся
showTotal(cart.total);                         // тот же объект, уже изменённый
```

</div>

<Example file="practice-08-after-move.js" />

Объект после возврата тот же самый (`===`), и в нём уже лежат изменения, сделанные в другом потоке. Если нужно что-то показать, пока задача идёт, заранее скопируйте нужные поля в обычные переменные.

С типизированными массивами в регионе ошибки не будет, но легко ошибиться тише: view, прочитанный до переезда, после него пустой, и после возврата региона таким и останется ([подробнее](/region-js/ru/guide/#typed-detach)). Перечитайте поле после `await`. Обращения к захваченному региону, пока задача идёт, подсвечивает правило ESLint [`no-region-use-while-spawned`](/region-js/ru/tooling/#no-region-use-while-spawned).

## <span class="practice-num">9</span> Много чисел — в типизированный массив {/* #typed */}

Доступ по индексу к массиву региона компилятор встраивает в машинный код, но на каждом обращении проверяет форму и границы, а при записи ещё и значение (практики [4б](#local-read) и [5](#methods)). Кроме того, массив значений хранит любые значения JS, и дробное число в нём — отдельный объект в общей куче. Типизированный массив в регионе устроен иначе. При чтении поля вы получаете обычный `Float64Array` над памятью региона ([подробнее](/region-js/ru/guide/#typed)), и цикл по нему компилируется так же, как по любому типизированному массиву. Проверка владельца одна, при чтении поля, а не на каждом элементе.

<div class="versus">

```js bad
const data = region.run(() => ({
  samples: Array.from({ length: N }, read),   // обычный массив чисел
}));
for (let i = 0; i < data.samples.length; i++) total += data.samples[i];
```

```js good
const data = region.run(() => ({
  samples: Float64Array.from({ length: N }, read),
}));
const samples = data.samples;                 // view один раз, до цикла
for (let i = 0; i < samples.length; i++) total += samples[i];
```

</div>

<Chart id="p-typed" />

<Example file="practice-09-typed-arrays.js" timing collapsed />

Сумма по `Float64Array` в регионе идёт с той же скоростью, что по обычному `Float64Array`, и в 2,1 раза быстрее, чем по массиву чисел в регионе. До встраивания доступа в компиляторы сумма по массиву региона занимала 6,9 мс, и разница была в 10 раз, до проверки владельца один раз на цикл — 2,4 мс и в 3,5 раза. Миллион записей в массив региона теперь занимает 2,0 мс (было около 8), в типизированный массив — около 1,7 мс, как и без регионов. Записи в `Float64Array` между запусками скачут от 0,8 до 1,7 мс, у обычного и у регионального одинаково. Выигрыш стал скромнее, но совет в силе: на чтении он всё ещё двукратный, типизированный массив занимает меньше памяти, а дробные числа в него пишутся без копии в общую кучу.

Две оговорки. Читайте поле один раз перед циклом: каждое чтение создаёт новый view, и делать это на каждом шаге незачем. И не держите view после переезда или заморозки региона: он отсоединится и будет читаться как пустой.

## <span class="practice-num">10</span> В `map` возвращать ручку задачи {/* #map */}

`Promise.all(items.map(...))` ждёт то, что вернул колбэк `map`. Если колбэк вызывает `spawn`, но возвращает что-то другое (номер, исходный элемент, ничего), `Promise.all` выполнится сразу, а задачи продолжат работать. Код после `await` решит, что всё готово, хотя это не так. Если задача упадёт, её ошибку тоже никто не поймает, и d8 сообщит о [необработанном отклонении](/region-js/ru/spawn/#unhandled).

<div class="versus">

```js bad
await Promise.all(parts.map((i) => {
  spawn(heavy, sizes[i]);     // ручка потерялась
  return i;                   // Promise.all ждёт число
}));
```

```js good
const results = await Promise.all(parts.map((i) =>
  spawn(heavy, sizes[i])));   // Promise.all ждёт задачи
// или, если нужно другое значение:
// parts.map((i) => spawn(heavy, sizes[i]).then(() => i))
```

</div>

<Example file="practice-10-map-handles.js" timing />

В плохом варианте `Promise.all` вернул номера частей, пока задачи только начинались: эти миллисекунды ушли на сами вызовы `spawn` и запуск воркеров пула. Задачи закончились намного позже, и узнать об этом удалось только через `spawn.idle()`. Эту ошибку подсвечивает правило ESLint [`no-floating-spawn`](/region-js/ru/tooling/#no-floating-spawn): оно отдельно говорит, что колбэк возвращает не ту ручку.

## <span class="practice-num">11</span> Билет в асинхронной задаче — через `borrowWhile` {/* #borrow-while */}

Билет `region.borrow()`, взятый в задаче `spawn`, сдаётся сам, когда задача закончилась. Для синхронной работы это то, что нужно. Но если задача отложила чтение на потом (таймер, `await` без возврата промиса), к этому моменту билета уже нет, и чтение бросит `OwnershipError`: без билета замороженный регион читать нельзя, а его к тому же могли разморозить. `region.borrowWhile(fn)` держит билет, пока не выполнится промис из `fn`. Главное — вернуть этот промис из задачи или дождаться его, иначе задача закончится раньше. Замера здесь нет: плохой вариант просто не работает. Пример с настоящим выводом — на [странице про spawn](/region-js/ru/spawn/#borrow).

<div class="versus">

```js bad
await spawn(() => {
  const ticket = Region.of(prices).borrow();
  setTimeout(() => show(prices.apple), 100);   // билет уже сдан
});
```

```js good
const apple = await spawn(() =>
  Region.of(prices).borrowWhile(async () => {
    await sleep(100);
    return prices.apple;                       // билет ещё у задачи
  }));
```

</div>

Голый билет, переживший задачу, d8 замечает при запуске и печатает в воркере предупреждение. `borrowWhile` с асинхронной функцией без `return` видно ещё в редакторе: его подсвечивает правило ESLint [`no-floating-borrow-while`](/region-js/ru/tooling/#no-floating-borrow-while).

## <span class="practice-num">12</span> Большой набор данных — литералами `#{}` или одним `run`, а не `run` на каждый объект {/* #build */}

Один объект, собранный обычным кодом, кладут в регион через `region.run(() => ({ ... }))` ([как](/region-js/ru/guide/#direct)). Но каждый вызов копирует то, что вернул: сначала движок создаёт обычный объект, потом его копию в регионе. На десятке объектов этого не видно, на сотнях тысяч видно хорошо.

Литерал `#{}` ничего не копирует и после первого объекта каждой формы создаёт объект прямо в машинном коде. Собирайте большой набор литералами. Если данные уже лежат обычными объектами, скопируйте их в регион одним `run`: одна копия всего набора дешевле копии на каждый объект.

<div class="versus">

```js bad
const items = region.run(() => []);
for (const row of rows) {                 // 200 000 строк
  items.push(region.run(() => ({ id: row.id, name: row.name,
    tags: [...row.tags], price: row.price })));
}
```

```js good
{
  using _ = region.enter();
  const items = #[];
  for (const row of rows) {               // без копии
    items.push(#{ id: row.id, name: row.name,
      tags: #[row.tags[0], row.tags[1]], price: row.price });
  }
}
// Данные уже есть обычными объектами: одна копия всего набора.
const items = region.run(() => rows.map((row) => ({
  id: row.id, name: row.name, tags: [...row.tags], price: row.price,
})));
```

</div>

<Chart id="p-build" />

<Example file="36-create.js" timing collapsed />

Литералы в 2,2 раза быстрее одного `run` и в 5 раз быстрее `run` на каждый объект. Один `run` в свою очередь в 2,3 раза быстрее, чем по одному. Читать потом все три массива почти одинаково быстро, около 1 мс за проход: объекты с одинаковыми ключами получают одну форму, каким бы способом их ни создали. Все четыре способа — на странице [«Цифры»](/region-js/ru/numbers/#create).

Добавлять отдельные объекты в готовый регион по ходу работы можно спокойно, это микросекунды на объект. Из двух способов литерал `#{}` дешевле, потому что не копирует.
