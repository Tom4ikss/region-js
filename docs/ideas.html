Chapter 2

The idea: data has an owner

Regions rest on one rule: at any moment, data has one owner, and only the owner can write to it. Everything else is a way to hand ownership to another thread or to let everyone look for a while.

One owner

Analogy: apartment keys

An apartment has one set of keys. Whoever has the keys gets in: lives there, moves the furniture, changes things. If you gave the keys to a friend, you can no longer get in yourself. But nobody copied or relocated the apartment: the only thing that changed is who holds the keys.

A region is that apartment. It holds a group of related objects: for example, a tree, its arrays, and its strings. One thread owns the region. Only that thread can read and modify these objects. Any other thread that tries to access them gets an OwnershipError.

The owner is assigned to the whole region at once, not to each object separately. That is why handing over a region of a million objects is as cheap as one of three: you hand over one set of keys, not a million.

Moving

Passing a region to another thread means handing over the keys. In code this is an ordinary postMessage, except that the region is listed in the transfer list: worker.postMessage(msg, [region]). This is how ArrayBuffer is passed today. spawn and channels hand over the keys on their own: a region that a task captured, or that was sent into a channel, moves without a transfer list.

A move can also return the region: the worker sends it to the main thread the same way. The objects stay the very same ones: === returns true.

Freezing: everyone can look

Sometimes you do not want to hand data to one thread but to let many threads read it at once. For example, a lookup table, settings, or a large tree that several workers search in parallel.

Analogy: a museum exhibit

An exhibit stands in a hall. Any number of visitors can look at it at the same time, and nobody gets in anyone's way. Nobody may touch it, not even the museum itself, while it is on display. To fix something, the exhibit first has to be taken off display.

region.freeze() puts the region on display. Now every thread that has taken a ticket (more on that below) can read it, and nobody can write to it, including the owner. Such a region can be sent to several workers with an ordinary postMessage without a transfer list: each one gets a reference to the same objects, with no copies.

region.thaw() takes the exhibit down: the owner can write again, and the others lose access. Only the one who put the exhibit on display can take it down. This right can be passed to another thread; the data itself does not go anywhere.

A visitor's ticket

Entry to the hall is by ticket: region.borrow(). Without a ticket, a frozen region can be read only by the one who put it on display. Other threads take a ticket, or else they get an OwnershipError. spawn tasks get a ticket automatically for the regions they receive.

While at least one ticket is out, the exhibit will not be taken down: thaw() throws an error, and thawWhenFree() waits for the last visitor. So the data does not change in the middle of your read. When you are done reading, hand the ticket back: release(). With the new using syntax it is returned automatically when the block exits.

All region states

There is also a final state: “freed”. After region.free() the region is inaccessible to everyone, forever, and its memory is released without waiting for the references to disappear (more).

And one more: “sealed”. This is freezing forever, with no right to thaw. Since the region will never change again, it can be read without borrows, and the garbage collector frees it when no references are left. This is how Arc<T> works in Rust (more).

Why this rules out data races

A data race happens when three conditions hold at once:

  1. two threads access the same memory,
  2. they do it at the same time,
  3. and at least one of them writes.

The region rules break this combination. Only the owner can write, and there is only one owner. When a region is frozen, many threads read, but nobody writes. When a region is in transit, it cannot even be read. The situation “one thread writes while another reads or writes at the same time” simply never arises.

What matters is that the engine checks this on every field access; it is not an agreement like “let's not touch this object from the worker”. You cannot make a mistake and accidentally read someone else's data: instead of a silently corrupted value, you get an exception.

Here is the same counter experiment as on the previous page, but with a region. Both workers hold a reference to one object and try to increment it a million times at the same time. Only worker A is made the owner.

Not a single write by worker B went through, while all of the owner's writes did. The total is exactly one million, no matter how many times you run this example. There are no Atomics or locks in the code.

What if two threads want to write?

Then the region is passed back and forth: one thread does its work and hands it over. Nobody waits: if a thread tries to write to a region it does not own, it gets an exception right away instead of joining a queue. This is a deliberate decision. There are no locks that wait at all, which means there are no deadlocks, where two threads wait for each other forever.

Why a region holds only data

A region can hold ordinary objects, arrays, typed arrays, strings, numbers, true/false, null, and undefined. Functions and instances of Map, Set, Date, and the like do not go in. The reason is simple: a function remembers the variables of the thread where it was created (its closure), and built-in objects like Map have their own internal layout inside the engine and are tied to their thread. They cannot be handed to another thread by reference without a copy. Ordinary data can: all it needs is the graph of fields itself.

Two exceptions were made on purpose. A function without a closure (Region.fn) is essentially its source text, and each thread compiles it itself. A LocalRef handle (Region.localRef) to an object of the creating thread moves together with the region, but the object itself stays at home, and the handle can be dereferenced only there, like SendWrapper in Rust (more).

If you know Rust

Moving is like a move, and freezing with borrows is like a shared borrow &T. The difference is that here everything is checked at run time, not by the compiler: you see a mistake as an exception, not as a build error.
