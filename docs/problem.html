Chapter 1

Why it is needed

JavaScript runs your code on one thread. While that thread is busy, the page does not respond. Workers give you a second thread, but you can only talk to it through copies of data. This page explains why it works this way and why that is inconvenient.

One thread and a task queue

A page has a main thread. Your JS runs on it, and the browser also handles clicks and draws frames on it. All of this sits in one queue: task after task, one at a time.

Analogy

Picture a store with one checkout. The cashier serves customers in turn. If one customer unloads a cart that takes half an hour, everyone else waits, even if all they hold is a single bottle of water. The cashier cannot turn to them in the middle of someone else's purchase.

For animation to stay smooth, the browser needs to draw a frame roughly every 16 ms. If your function computes for 800 ms (parsing a large JSON, building a search index, computing a graph layout), no frames are drawn and clicks wait the whole time. The user sees a frozen page.

Web Workers: a second thread, but a world of its own

Heavy work can be moved to a Web Worker. It is a separate thread with its own JS. Meanwhile the main thread is free and draws frames.

But a worker has its own memory. It does not see your variables and objects: in the engine, each thread has its own heap (the place where objects live) and its own global objects. There is only one connection: messages through postMessage.

postMessage copies

When you write worker.postMessage(data), the browser performs a structured clone: it walks the whole object graph, writes it out as bytes, and rebuilds it on the worker's side. The receiver holds a copy. If it changes something in the copy, nothing changes for the sender.

A copy is safe: each thread has its own data, so they have no way to interfere with each other. But it is slow. A tree of a million nodes takes almost a second to copy (928 ms in our measurements). If you need to send data to a worker, process it, and send it back, you pay twice. And part of this work is done by the main thread, the very checkout we wanted to relieve.

Analogy

You send a folder of documents to a colleague in another office. The courier cannot take the original, so the whole folder is photocopied. The thicker the folder, the longer you wait. And your colleague's notes stay on their copy: they do not change yours.

Transferable: no copy, but only bytes

There is an exception for ArrayBuffer: you can pass it in the transfer list, postMessage(buf, [buf]). Then there is no copy; the buffer simply changes hands, and the sender's buffer becomes empty. This is fast, but it works only with raw bytes. Objects, arrays of objects, and strings cannot be passed this way: you first have to encode them into bytes yourself.

SharedArrayBuffer: shared memory and races

SharedArrayBuffer goes further. It is a chunk of memory that several threads see at once. Nothing needs to be copied, but again it holds only bytes. There are no objects in it; you lay out the data at offsets yourself. In the browser it is also available only on pages with special headers (cross-origin isolation).

The main problem lies elsewhere. When two threads write to the same memory at the same time, you get a data race. Here are two workers that each increment the same counter a million times:

Without Atomics, the counter did not reach two million: some of the increments were lost. How many differs from run to run. The reason is that c[0] = c[0] + 1 is three steps: read, add, write. Both threads read, say, 10, both add one, and both write 11. One increment is lost.

Analogy

Two cashiers keep a shared tally in one notebook. Both look at the same moment: “the notebook says 10”. Each adds one and each writes down “11”. Two items were sold, but the notebook shows one more. Neither cashier made a mistake; the mistake is that they used the notebook at the same time.

Atomics.add makes the increment indivisible, and the count comes out right. But this works for a single number. A complex structure (a tree, a list, an object with fields) needs locks, and locks are easy to get wrong: forget to take a lock, take two locks in different orders and hang forever. Such bugs show up rarely, at random, and are almost impossible to reproduce.

What we have today

MethodWhat can be passedCost of passingSafety
postMessage(data)almost any dataa copy, grows with sizesafe: each side has its own copy
transfer ArrayBufferbytes onlyalmost zerosafe: the sender loses the buffer
SharedArrayBufferbytes onlyzero, the memory is sharedraces are possible; needs Atomics and locks
Regions (this experiment)objects, arrays, strings, numbers, typed arraysalmost zero, independent of sizethe engine lets only the owner access the data

Regions try to combine the convenience of the first method with the speed of the second. Objects remain ordinary JS objects, with fields, nesting, and strings. They are passed like an ArrayBuffer in a transfer list, that is, they change hands without a copy. spawn and channels pass them this way on their own, without a transfer list. And there are no races, because the engine does not let two threads touch the data at the same time if at least one of them writes. How exactly is explained on the next page.
